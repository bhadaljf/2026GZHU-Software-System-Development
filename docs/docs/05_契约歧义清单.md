# 契约歧义清单（第 1 阶段）

> 用途：记录人工推演中发现的规则歧义、任务书未明确之处、以及本稿为了继续推演而采用的**临时口径**。
> 原则：不把临时口径写成已确认规则；每条都给出两种可能解释、对预期的影响、建议确认人。
> 状态：全部未关闭。确认后再改 `expected.json`，不能反过来用系统输出改预期。

## A-01 计划切分的整数化与“每条计划 1—3 人”冲突

- **歧义点**：A/B 总计划要同时满足“自招不超过 10%”“名额分配为总计划 50%”“每条计划 1—3 人”“自招非空”。按整数切分，这四个条件不能同时成立。
- **两种可能解释**：
  1. **严格 10%/50%**：总计划至少 10 才能让自招 1 人不超过 10%；此时第三批统招 = 10−1−5 = 4 人，超出“1—3 人”。
  2. **严格 1—3 人**：总计划取 8，自招 1 人（12.5%，超过 10%）；或总计划取 6，自招 0 人（c05 失去自招对象）；或把第三批 4 人拆成两个 2 人计划（任务书只要求每校在一个批次接收统招，未明确允许拆计划）。
- **对预期的影响**：影响 A/B 第三批初始名额、A-T/B-T 的 `carry_in`、`remaining`；c08、c10 的余额数字会变。c02、c03、c05 的录取集合不直接受影响；c04 的 D/C 边界不受影响。
- **本稿临时口径**：采用解释 1，A/B 总计划 10、自招 1、名额 5、第三批统招 4；在 README 与所有相关 case 中披露 4 人与“1—3 人”的冲突，不暗改。
- **建议找谁确认**：1 号（契约/需求负责人）主确认；涉及任务书原意时请组长向任课教师确认；2 号复核计划表字段。

## A-02 第一批未完成自主招生计划是否随第二批一起结转

- **歧义点**：任务书 §三.4 写“第一、第二批结束后，未完成名额并入本校指定的第三或第四批统招计划……且只结转一次”；统一规则 U06 只详细写“名额分配……第二批结束后先汇总各初中余额，再一次性转入本校第三批统招”，没有单独说第一批余额。
- **两种可能解释**：
  1. **第一、二批都结转**：A-Z1/B-Z1 的未完成名额与第二批各初中余额合并，转入 A-T/B-T；本稿采用此解释，依据任务书 §三.4 的明文。
  2. **只结转第二批名额分配**：第一批未完成名额不转，直接作废；依据是 U06 只提名额分配。
- **对预期的影响**：c02、c03、c04、c08、c10 的 A-T/B-T `carry_in` 和 `remaining` 都会变。例如 c08：本稿 A/B 各转入 5；若只转第二批，各转入 4，A-T `remaining` 7、B-T `remaining` 8。c09 的空结果也会受影响。
- **本稿临时口径**：解释 1（第一、二批都结转）。
- **建议找谁确认**：1 号主确认；2 号确认结转流水是否允许“第一批余额”作为独立来源；组长核对任务书 §三.4 原意。

## A-03 结转后的名额适用哪条计划控制线

- **歧义点**：A-Z1 的控制线是 680、B-Z1 是 660；A-T/B-T 的控制线是 600；A-Q-J1/J2、B-Q-J1/J2 的控制线也是 600。自招或名额分配的余额转入第三批后，这些名额是“变成第三批计划的一部分”，还是“保留原计划控制线”，任务书没有明说。
- **两种可能解释**：
  1. **适用第三批计划控制线**（本稿）：转入 A-T 的名额按 A-T 的 600 判断；转入 B-T 的按 600。依据是“并入本校第三批统招计划”，名额身份随计划改变。
  2. **保留原计划控制线**：自招余额仍要求 680/660，名额分配余额仍要求原名额计划控制线；或者取“原线”和“第三批线”中较严者。
- **对预期的影响**：本阶段 c08 的 S13 为 690，高于 680 和 600，两种解释都录取，故 c08 不区分；若换成 650—679 的考生，解释 1 录、解释 2 不录。后续补 c09/结转边界 case 时必须先冻结此口径。
- **本稿临时口径**：解释 1（第三批计划控制线 600）。c08 特意避开 650—679，避免把未确认口径写成确定预期。
- **建议找谁确认**：1 号主确认；2 号给出“结转名额”在计划表/录取记录中的字段表达；涉及“计划控制线”定义时请任课教师确认。

## A-04 同分序号的唯一范围：全市还是校内

- **歧义点**：任务书 §三.3 说“同分序号，同一总分内序号唯一、数值越小优先”，没有说唯一范围是全市、区内还是校内；数据模型只要求考生有“同分序号”。
- **两种可能解释**：
  1. **全市唯一**：所有考生同一总分内序号不重复；跨初中同分竞争同一统招计划时可直接比较。
  2. **校内唯一**：每所初中内部同一总分内序号唯一；跨初中同分时需要额外的全市排序键，或者不能直接比较。
- **对预期的影响**：本稿 20 人的同分序号取 1—20 全局唯一，是比“同一总分内唯一”更强的约束。c03 的同分双方 S05、S19 都是 J2，不受范围影响；若未来让 J1、J2 同分考生竞争同一统招计划，解释 2 会使排序不确定。
- **本稿临时口径**：全市唯一；但只在同校内同分场景做确定断言，跨校同分留到第 2 阶段。
- **建议找谁确认**：1 号主确认；2 号确认生成规则是否按全市或按校；若按校，需补“跨校同分”排序键。

## A-05 `admit_order` 是全局顺序还是计划内顺序

- **歧义点**：`expected.json` 要求 `admit_order`，但没定义它是“一次运行内全局递增”还是“每个计划内部从 1 开始”。任务书只说“投档顺序”，未明确粒度。
- **两种可能解释**：
  1. **全局顺序**（本稿）：一次运行内从 1 开始；同一梯度、同一志愿轮次内按计划 ID 升序处理不同计划，因此会出现“低分先于高分”的跨计划顺序。
  2. **计划内顺序**：每个计划各自从 1 开始；跨计划不可比，`last_student` 取该计划内最大序号。
- **对预期的影响**：不改变任何计划的录取集合、最低分、末位考生；只改变 `admit_order` 的数字。c02 中 S20 的顺序 4 早于 S02 的顺序 5，是同一 T2 第 1 志愿轮次内 A-Q-J1 先于 B-Q-J1 的结果；若改为计划内编号，A-Q-J1 为 1/2/3，B-Q-J1 为 1/2。
- **本稿临时口径**：全局顺序；同一梯度/志愿轮次内计划 ID 升序。`last_student` 仍按计划内实际录取顺序取最后一人，两者不矛盾。
- **建议找谁确认**：2 号（引擎/结果表）主确认；1 号确认 JSON 契约；若前端要显示“第几名”，需统一。

## A-06 志愿序号能否空缺或不连续

- **歧义点**：c04 为了制造“低 1 分者第 1 志愿、压线者第 2 志愿”的边界对照，让 S01、S16、S09 只填第 2 志愿（`vol_seq=1` 空缺）。任务书只给志愿上限，没有说必须从 1 连续填报。
- **两种可能解释**：
  1. **允许空缺/不连续**（本稿）：空缺表示未填，不生成志愿记录；第 2 志愿仍按第 2 志愿轮次处理。
  2. **必须从 1 连续**：缺少第 1 志愿的记录视为无效数据，运行前拒绝，或自动把第 2 志愿上移为第 1 志愿。
- **对预期的影响**：若必须连续，c04 的三名考生需要补一个不会录取的第 1 志愿；`vol_seq` 和 `admit_order` 会变，但 720/719、680/679、600/599 的录取归属不应变。若系统拒绝整单，c04 当前数据不能直接运行。
- **本稿临时口径**：允许空缺；c04 明确标注“依赖 A-06”。
- **建议找谁确认**：1 号主确认；2 号确认志愿表校验规则；若前端表单强制连续，应改 c04 构造而不是改预期结果。

## A-07 `expected.json` 固定字段没有末位同分序号

- **歧义点**：任务书 §四.3 要求末位考生“另外报告其总分、志愿序号和同分序号”；但题设给的 `expected_stats` 固定字段只有 `min_score`、`last_student`、`last_score`、`last_vol_seq`，没有 `last_tie_seq`。
- **两种可能解释**：
  1. **严格按固定 schema**（本稿）：不新增字段；末位同分序号写在 `case.md` 结论表和自检块中，JSON 只断言到志愿序号。
  2. **扩展 schema**：增加 `last_tie_seq`，让 JSON 也能直接对照同分序号；但这违反“字段固定”的字面要求。
- **对预期的影响**：不影响录取结果；影响自动化对照能否直接验证“末位同分序号”。c03、c04、c05、c08、c10 的末位同分序号目前只在 Markdown 中。
- **本稿临时口径**：解释 1；不擅自扩展 JSON。
- **建议找谁确认**：1 号主确认契约字段；2 号确认对照脚本是否允许额外字段；若允许，第 2 阶段统一加 `last_tie_seq`。

## A-08 越界名额志愿：运行前拒绝还是运行中跳过

- **歧义点**：c03 放了一名 J1 考生 S04 填 A-Q-J2（J2 名额）。这既可以是“非法志愿/无效计划”，也可以是“合法填报但不具资格”。任务书要求“跨初中不得挤占”，但没有说处理位置。
- **两种可能解释**：
  1. **运行中跳过**（本稿）：志愿记录保留，进入候选池前按初中过滤；不占名额，记 `QUOTA_SCOPE_MISMATCH`。
  2. **运行前拒绝**：输入校验阶段整单拒绝，或删除该志愿后再运行；不产生投档记录。
- **对预期的影响**：c03 的 S05、S19 录取不变；S04 的原因码/呈现位置会变。若系统整单拒绝，c03 当前数据无法直接跑，需要先修数据。若系统错误地允许 S04 进入候选池，他会以 700/seq4 挤掉 S19，这是本 case 要抓的核心错误。
- **本稿临时口径**：解释 1（跳过并记原因码）；不把“拒绝整单”当成已确认行为。
- **建议找谁确认**：1 号主确认“无效志愿”的验收口径；2 号确认校验层与投档层的职责边界；c11 异常输入 case 一并定稿。

## A-09 空计划的 `last_score` 用什么值

- **歧义点**：题设只说“无人录取时 `min_score` 和 `last_student` 用字符串 `"无"`”，没有说 `last_score` 和 `last_vol_seq` 怎么填。
- **两种可能解释**：
  1. **统一空值语义**（本稿）：`last_score="无"`、`last_vol_seq=null`；与 `min_score`、`last_student` 保持同一种“无人”表达。
  2. **数值字段用 null**：`last_score=null`、`last_vol_seq=null`；只有字符串字段用 `"无"`。
- **对预期的影响**：不影响录取，只影响 46 条空计划统计行的 JSON 对照；若 2 号按 null 实现，会产生 46 条假失败。
- **本稿临时口径**：解释 1；`min_score`、`last_student`、`last_score` 三者统一 `"无"`，`last_vol_seq=null`。
- **建议找谁确认**：1 号确认 JSON 空值契约；2 号确认序列化实现；对照脚本按确认后的类型做归一化，不能把 `"无"` 和 0 当成等价。

## 确认顺序建议

1. 先确认 A-01（计划切分）与 A-02（第一批是否结转），因为它们会改所有 A/B 余额。
2. 再确认 A-03（结转控制线）与 A-04（同分序号范围），它们会影响后续补的边界 case。
3. 最后确认 A-05—A-09（JSON 契约、志愿空缺、越界处理、空值），它们主要影响对照脚本，不影响已完成的录取集合。
4. 每条确认结果都要回写到本文件对应条目，并同步修改 `README.md` 与相关 `expected.json`；不得只改系统实现、不改预期。
