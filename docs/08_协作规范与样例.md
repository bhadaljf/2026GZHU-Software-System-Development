# 08 协作规范与样例

维护人：1 号　适用：全体　版本：v1.0（第 1 周冻结）

本文件解决一件事：每个人交出的东西，下游能直接接着用。规范给规则，样例给可以直接照抄的格式。

## 2 命名与目录

- 文档：`docs/编号_名称.md`，编号固定（00—08），不新建编号。
- 代码：模块名用英文小写，`src/engine/batch_runner.py` 这类；一个文件一个职责。
- 数据：`<类别>_<规模>_v<版本>.csv`，如 `students_small_v1.csv`。
- 用例：`test/cases/c05_同梯度志愿优先/`，目录名带编号与短语。
- 导出与演示：带日期与数据编号，如 `export/admit_20261210_RUN20261210-01.csv`。

## 3 Git 规范

分支：`main` 只放可运行版本；`dev` 集成；个人 `feature/<编号>-<短语>`、`fix/<编号>-<短语>`、`docs/<短语>`。

```bash
git switch -c feature/3-engine-batch-loop
git switch dev && git merge --no-ff feature/3-engine-batch-loop
```

提交信息：`类型: 模块 - 内容（依据）`，类型取 `feat/fix/docs/test/refactor`，依据写规则条款或缺陷编号。

```
feat: engine - 实现第三批志愿轮次循环（R12, R13）
fix: query - 末位考生取最后一次录取而非最低分（iss-017）
docs: contract - 登记 admit_result 新增 admit_order（契约变更 #3）
test: case - 补同梯度低分第一志愿优先用例（TC-05）
```

合并前自查：改动可追溯到条款或缺陷；未改字段语义；涉及规则/结转/口径的改动带用例；小数据集重跑与预期一致；无真实个人信息与密钥。

## 4 契约变更

字段冻结后只增不改。新增字段按四步走：提出 → 登记 → 告知 → 同步。

1. 提出人在组会说明用途与影响面。
2. 1 号在 `docs/00_契约.md` 第 6 节登记，一行一条：

| 日期 | 提出人 | 对象 | 变更 | 原因 | 影响方 | 确认 |
| --- | --- | --- | --- | --- | --- | --- |
| 11.27 | 4 号 | admit_result | 新增 admit_order int | 末位考生需按录取顺序取最后一条 | 3 号、6 号 | 3 号已确认 |

3. 2 号改 `db/schema.sql` 或 3 号改 `db/schema_log.sql`，并补迁移说明。
4. 消费方（4 号、6 号）当日跟进；未跟进前旧字段保持可用。

## 5 数据交接样例

小数据集四张表，表头固定，编码 UTF-8，逗号分隔。示例与任务书“最低测试示例”一致（G₁=720、第二梯度 680、L=600，A 校统招 2 人）。

`students.csv`

```csv
student_id,name,junior_school_id,score,tie_seq
S01,甲,J1,690,1
S02,乙,J2,710,1
```

`plans.csv`

```csv
plan_id,year,high_school_id,batch,category,quota,control_line,remaining
P-A3,2026,H-A,3,统招,2,600,2
```

`volunteers.csv`

```csv
year,student_id,batch,seq,plan_id
2026,S01,3,1,P-A3
2026,S02,3,1,P-B3
2026,S02,3,2,P-A3
```

`eligibility.csv`（无自主招生时仅留表头）

```csv
student_id,high_school_id,status,rank
```

交接要求：表头与契约字段一致；分数为整数；空值写空不写 0；每份数据集附 `README` 说明版本、种子与生成命令。

## 6 接口交接样例

查询考生结果：`GET /api/students/S01/result?run_id=RUN20261210-01`

```json
{
  "run_id": "RUN20261210-01",
  "student_id": "S01",
  "score": 690,
  "tie_seq": 1,
  "admitted": true,
  "batch": 3,
  "plan_id": "P-A3",
  "school": "A 校",
  "volunteer_no": 1,
  "admit_order": 1,
  "volunteers": [
    {"batch": 3, "seq": 1, "plan_id": "P-A3", "status": "admitted", "reason_code": null},
    {"batch": 3, "seq": 2, "plan_id": "P-C3", "status": "skipped", "reason_code": "R04"}
  ]
}
```

未录取者的 `admitted` 为 `false`，`batch`、`plan_id`、`volunteer_no` 为 `null`，原因写在对应志愿的 `reason_code`。

按计划查名单：`GET /api/plans/P-A3/admissions?run_id=...&page=1&size=100`

```json
{
  "plan_id": "P-A3",
  "quota": 2,
  "admitted_count": 2,
  "remaining": 0,
  "min_score": 690,
  "last_admitted": {"student_id": "S02", "score": 710, "tie_seq": 1, "volunteer_no": 2},
  "items": [
    {"admit_order": 1, "student_id": "S01", "score": 690, "volunteer_no": 1},
    {"admit_order": 2, "student_id": "S02", "score": 710, "volunteer_no": 2}
  ],
  "page": 1, "size": 100, "total": 2
}
```

口径约定：`min_score` 与 `last_admitted` 分别计算，可能不是同一人（上例中最低分是甲 690，末位是乙 710）；无人录取时二者均返回 `null`，界面显示“无”。

## 8 任务、缺陷与用例

用 `docs/templates/` 里的模板，不自由发挥。最小要求：

- 任务卡：编号、标题、归属规则条款、负责人、依赖、验收、预计工时。
- 缺陷：编号、数据集与快照、复现步骤、期望、实际、涉及条款、影响范围、负责人。
- 用例：编号、场景类别、数据目录、输入要点、人工预期、实际、结论。

人工预期必须在跑系统之前写定。发现实际与预期不符时，先确认预期是否写错，再判断代码问题；不得改预期去迁就输出。

## 9 周报与会议

每周五下班前交周报（模板 `docs/templates/周报.md`），四条：本周完成、下周计划、阻塞、需要谁配合。组会 20 分钟，只过阻塞与跨人依赖，逐条结论记入周报附录。

## 10 演示与交付

- 视频：1080p 及以上，界面字号不小于 14pt，成片 8—12 分钟，含一次完整投档与两个边界场景；命名 `demo/演示视频_v1_20261214.mp4`。
- 提交清单：源码与脚本、`db/`、`docs/`（00—08）、`test/`、`deploy/README.md`、`demo/`。
- 提交前由 1 号按 `README.md` 的文档索引逐项打钩；缺件按未完成处理。

## 11 禁止事项

- 不直连他人的表：查询层只读 `admit_result` 与 `admit_log`，界面只读接口。
- 不私改契约字段语义；新增字段必须登记。
- 不用系统输出反填人工预期，不伪造测试记录。
- 不提交真实个人信息、密钥与 `.env`；大文件（15 万数据、视频）不入库。
- 不在引擎内临时算计划切分；计划数以 `plan` 表为准。
